# 개인 PC 2 단독 작업 계획

## 목적

팀원이 함께 있지 않아도 개인 PC 2 소유 범위에서 안전하게 진행할 수 있는 작업을 정리한다. 다른 PC 소스와 공유 인터페이스는 수정하지 않는다.

## 작업 승인 및 소유권

- 작업 전 실행 PC가 개인 PC 2인지 확인하고 대상 파일이 개인 PC 2의 실행·유지 범위에 속하는지 확인한다.
- 파일 생성·수정·이동·삭제 전에는 대상 파일과 변경 범위를 사용자에게 제시해 명시적 승인을 받는다.
- 분석·검토·계획·읽기 요청과 테스트 실행 승인은 소스 수정 승인으로 간주하지 않는다.
- 승인된 파일이나 범위를 넘어서는 작업이 필요하면 추가 승인을 받는다.
- 다른 PC 소유 소스의 변경이 필요하면 직접 수정하지 않고 해당 PC 소유자에게 변경 검토를 요청한다.
- 변경 검토 요청에는 대상 파일과 함수, 관찰된 문제, 제안 동작, 인터페이스 영향 및 검증 절차를 포함한다.
- `appleproj_interfaces/`, 저장소의 `docs/`, `README.md`, `AGENTS.md` 및 공통 빌드·네트워크 설정은 공유 파일로 취급한다.
- 공유 파일은 정확한 파일과 범위의 승인을 받은 경우에만 수정하고, 수정 후 영향받는 모든 PC를 보고한다.
- 수정 후에는 변경 파일과 수행한 검증을 보고한다.

## 우선순위 1: 단위 테스트 보강

- 모니터 상태의 정상, 중복, 순서 오류 및 ID 불일치 시나리오를 검증한다.
- 여러 사과의 deadline이 서로 영향을 주지 않는지 검증한다.
- 결과 요약에서 중복 결과를 별도 집계하는지 검증한다.
- 푸셔 선택에서 `VALID`만 선택 대상이 되는지 검증한다.
- 이벤트 이력이 simulation time과 wall time을 분리해 저장하는지 검증한다.
- 재검사 CLI의 빈 입력, 서비스 미가용, timeout, 거부 및 future 예외를 검증한다.

## 우선순위 2: 운영자용 결과 요약

- 전체 수신 메시지 수를 집계한다.
- 고유 검사 수와 중복 메시지 수를 구분한다.
- 등급별·상태별 개수를 집계한다.
- 사과별 가장 최근 검사 결과를 유지한다.
- 기존 `quality_monitor.py`와 연결하기 전에는 ROS 독립 모듈로 검증한다.

## 우선순위 3: 이력 저장

- 사용자가 명시하고 생성·append 동작을 승인한 경로에만 JSON Lines 형식으로 기록한다.
- simulation timestamp와 수신 wall timestamp를 모두 기록한다.
- 파일 경로, 회전 주기 및 보관 기간은 운영 합의 전까지 고정하지 않는다.
- 기본 모니터 노드에 자동 연결하지 않고 선택 기능으로 유지한다.

## 우선순위 4: 재검사 운용성

- 요청 전에 ID와 사유를 검증한다.
- 성공·거부·미가용·timeout·예외를 서로 다른 결과로 표시한다.
- 원래 검사 ID와 새 검사 ID의 관계를 기록할 방식을 준비한다.
- 자동 재시도 횟수는 합의 전까지 도입하지 않는다.

## 우선순위 5: 푸셔 선택 선행 구현

- 공유 전송 계약과 분리된 의미 기반 선택 로직을 작성한다.
- `VALID`의 `HIGH`, `MEDIUM`, `LOW`만 선택한다.
- 나머지 상태는 모두 라인 끝 통과로 결정한다.
- 중복 결과와 충돌 결과를 구분한다.
- 최종 `pusher_id`와 ROS 전송은 계약 확정 후 구현한다.

## 우선순위 6: 오프라인 연동 준비

- 개발 전용 mock 발행기로 정상·오류 품질 결과를 만들 수 있게 한다.
- 실제 GPU PC 발행기와 동시에 사용하지 않는다.
- checkpoint ID가 필요한 시나리오는 값을 명시적으로 입력하도록 한다.
- mock 데이터는 성능 평가나 최종 품질 판단 근거로 사용하지 않는다.

## 단독으로 결정하면 안 되는 항목

- 공유 메시지·서비스·액션 정의
- QoS의 최종 값
- deadline 시작 checkpoint ID
- `SortCommand` 전송 방식 및 최종 필드
- 실제 `pusher_id` 값
- GPU PC 1의 푸셔 동작 조건
- GPU PC 2의 품질 추론 정책
- 네트워크 timeout과 장애 복구 정책

## 권장 작업 순서

1. ROS 독립 모듈의 코드 검토
2. 단위 테스트 대상과 `build/`, `install/`, `log/` 생성·갱신 범위를 제시하고 실행 승인 확보
3. 결과 요약을 모니터 노드에 연결할지 결정
4. 이벤트 저장 경로와 운용 정책 합의
5. mock 기반 개인 PC 2 자체 연동 확인
6. 팀 회의에서 공유 계약 확정
7. 확정 계약에 맞춰 실제 통합 구현
